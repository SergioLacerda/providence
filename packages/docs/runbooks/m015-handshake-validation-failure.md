# M015 Handshake Validation Failure

Verification state: incident-backed

## Symptoms

- `providence governance validate` reports `Active handshake (M015): FAIL`.
- Structure, fingerprints, artifact consistency, and runtime preflight all pass;
  only the handshake row fails.
- The failure recurs shortly after being "fixed" (a new
  `governance handshake --init` / `--response` makes it pass, then it fails
  again later in the same session).
- `git push` fails locally at the pre-push hook's governance step, but the
  same repository state passes in CI.

## Diagnosis

M015 checks two different things, and only one of them is artifact integrity:

- **Artifact lane**: structure, file access, fingerprints, conflicts, artifact
  consistency, runtime preflight, root-seed drift. This is what
  `providence governance validate --skip-handshake` checks, and what CI's
  `reusable-test.yml` / `sdd-validation.yml` jobs run.
- **Session lane**: whether `.providence/runtime/handshake-response.json` is
  still bound to the current `.providence/runtime/handshake-challenge.json`
  (same `challenge_id`/`session_id`), the response's `expires_at` has not
  passed, and the recorded `governance_fingerprint` still matches. Plain
  `providence governance validate` (no `--skip-handshake`) checks both lanes.

Known causes of session-lane failure, roughly in likelihood order:

1. **A pytest run rewrote the live challenge.** `AgentHandshakeProtocol()`
   with no `project_root` resolves to the real repository root (via cwd). Any
   test that constructs it that way and calls `generate_challenge(...)`
   persists a fresh `challenge_id`/`session_id` to
   `.providence/runtime/handshake-challenge.json`, which immediately
   invalidates any handshake response bound to the previous challenge. This
   was the confirmed root cause behind
   `.analysis/refined/20260912-m015-handshake-runtime-drift/`: a single test
   (`packages/core/providence_runtime/tests/test_handshake_enforcement.py::
   test_handshake_challenge_generation`) reproduced this by itself. A
   repository-root `conftest.py` guard (`_forbid_repo_sdd_writes`) now blocks
   this class of write repo-wide; `packages/core/providence_core/tests/
   test_handshake_repo_root_isolation.py` is the regression test.
2. **`providence governance generate --full-bootstrap` ran in this
   workspace.** It calls `complete_bootstrap_handshake()`, which issues a new
   challenge and completes it with `agent_id: bootstrap`. This overwrites
   whatever handshake response the current agent/human session had
   completed. `tools/maintenance/make_tasks.py::run_governance_bootstrap()`
   runs this. It is intentional bootstrap behavior, not a bug — but it means
   redo `governance handshake --init`/`--response` afterward if you need an
   active session handshake again.
3. **The response's authorization TTL (60 minutes,
   `_AUTHORIZATION_TTL_MINUTES` in `handshake_challenge.py`) expired.** A
   handshake response is not valid indefinitely once submitted.

To tell which one happened, compare
`.providence/runtime/handshake-challenge.json`'s `issued_at`/`session_id`
against `.providence/runtime/handshake-response.json`'s recorded values:

```bash
cat .providence/runtime/handshake-challenge.json
cat .providence/runtime/handshake-response.json
```

A `session_id`/`challenge_id` mismatch points to cause 1 or 2 (something
issued a new challenge). Matching IDs with a past `expires_at` points to
cause 3.

Run validation with a writable `uv` cache to rule out an unrelated
environment failure masquerading as M015:

```bash
UV_CACHE_DIR=/tmp/uv-cache uv run providence governance validate
```

## Resolution Steps

1. If you only need CI/artifact-integrity confidence (not an active agent
   session), use the artifact lane and stop here:

   ```bash
   UV_CACHE_DIR=/tmp/uv-cache uv run providence governance validate --skip-handshake
   ```

2. If you need an active session handshake (hard-mode agent execution),
   redo the handshake:

   ```bash
   uv run providence governance handshake --init
   # read the challenge, then:
   uv run providence governance handshake --response '<json response>'
   ```

3. If this happened during local development because you ran the full
   pytest suite or `providence governance generate --full-bootstrap`, that is
   expected — those commands intentionally exercise/rewrite the runtime
   handshake. Treat step 2 as the normal follow-up, not a workaround.

## Rollback

There is no destructive state to roll back: `.providence/runtime/` is
session-scoped, gitignored, and regenerated by the handshake commands above.
Do not attempt to hand-edit
`.providence/runtime/handshake-challenge.json` or
`.providence/runtime/handshake-response.json` — regenerate them through the
CLI instead.

## Post-Incident

- If a *new* test or tool is found writing to the real
  `.providence/runtime/` (mtime changes on `handshake-challenge.json` or
  `handshake-response.json` after running it outside `tmp_path`), that is a
  regression in test isolation, not expected M015 behavior. Fix the test to
  pass an explicit `project_root=tmp_path` (or `SDD_WORKSPACE_ROOT`-derived
  path) instead of relying on `AgentHandshakeProtocol()`'s cwd-based default.
- Record recurring local pre-push M015 failures in
  `docs/incidents/FAILURE_LEDGER.md` if they keep surfacing after this
  runbook's steps.
